# 第一阶段架构与后续工作

## 四层结构

```text
入口层       FastAPI / OpenAPI 交互文档；原有 CLI
服务层       申请与版本、规则审核、人工复核、交接、文档和问答、审计
编排层       规则引擎；文档向量检索 → 摘录或可配置模型 → 引用
数据模型层   SQLAlchemy 异步访问；SQLite 或 PostgreSQL + pgvector
```

规则结果与模型回答均为辅助意见，采购与安全决定由授权人员线下执行。审核输入中的目录、证据标记和过期阈值是调用方提供的模拟数据，不是经验证的正式来源。

## 数据模型

- `users`：演示用户、角色和令牌哈希。
- `procurement_requests`、`request_versions`：业务编号和不可覆盖的申请版本快照。
- `review_results`：审核结果、目录快照、检查日期、规则版本和一次人工意见。
- `handoffs`：申请版本、发起人、接收人、未解决事项、确认时间。
- `policy_documents`、`document_chunks`：制度名称、版本、来源、状态、分段及向量。
- `conversations`、`messages`：用户会话、消息及引用。
- `audit_logs`：关键操作人、类型、对象和时间。

数据模型使用的当前规则版本为 `1`；后续规则改变时必须同步更新版本并通过迁移和回归测试。证据目前以申请字段声明和目录快照表示，尚无单独证据文件表。

## 角色

申请人管理自己的申请和会话；审核人可查看申请、人工记录意见和确认指定交接；安全人员可查看申请并确认指定交接；管理员管理制度文档，但不自动拥有采购记录或安全审批权限。制度目前统一向已登录用户开放，尚未实现文档级权限。

## 待建设

- 正式用户身份、权限分组、文档级授权、审计防篡改、备份和保留策略。
- 用正式接口只读接入采购平台、ERP 和库存，明确映射、数据时效和故障回退；验证审批及温度证据来源。
- 正式制度文档上传解析、有效期与发布审批、向量模型版本迁移、检索质量评估和数据库向量索引。
- 对实际试点设计规则配置管理、审核记录的并发保护、可观测性、迁移机制和生产部署。
- 面向各角色的业务页面、通知、异常升级及经授权的安全停止流程。
- 核实 20 种试剂范围、评估样本、预算、安全责任和验收指标，再进行真实试点。
